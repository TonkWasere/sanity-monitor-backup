# cron_specs — эталон крон-циклов на гите (решение автора 24.10.2026)

## Зачем
Три cron-задачи мониторинга (часовой раунд + SNAP15 + SNAP35) живут ТОЛЬКО в планировщике
агента — до сих пор их определения нигде не хранились: при потере крон-хоста/удалении задач/
порче промпта восстановление было возможно только из памяти агента или переписки с автором.
Теперь эталон лежит в гите (`jobs.json`) — гит главнее всего, переживает любые вайпы ВМ,
и часовой раунд каждый час СВЕРЯЕТ живые кроны со спекой и самолично чинит несовпадения.

## Файлы
- `jobs.json` — эталон 3 задач: name, schedule (kind/expr/tz), payload.message ЦЕЛИКОМ,
  message_sha256 (быстрая сверка), last_known_job_id (справочно), priority, notes.
- `../../scripts/build_cron_specs.py` — генератор спеки. Правило: после ЛЮБОГО изменения
  промпта/расписания крона — перегенерировать (`python3 scripts/build_cron_specs.py`) и
  закоммитить, иначе следующий часовой раунд откатит живой крон к старой спеке.

## АВТОРИТЕТНОСТЬ ПОЛЕЙ
- АВТОРИТЕТНЫ: `name`, `schedule.kind/expr/tz`, `payload.kind`, `payload.message`
  (сверка по sha256 — полный текст промпта в логи/работу печатать не нужно).
- СПРАВОЧНЫЕ (не сверяются): `last_known_job_id`, `run_count`, даты — job_id меняется
  при каждом пересоздании, это НОРМА.
- Задачи вне спеки (созданные автором вручную потом) — НЕ ТРОГАТЬ: сверка управляет
  ТОЛЬКО тремя задачами по name-матчу.

## ПРОТОКОЛ СВЕРКИ (шаг 0c часового раунда — делает агент крон-инструментом)
1. `cron list` → сопоставить 3 name из jobs.json.
2. Для каждой: schedule.kind/expr/tz + sha256(payload.message) == message_sha256 из спеки.
3. Исходы:
   - **3/3 совпали** → тишина, в worklog ничего (или одна буква «crons 3/3 ok» в Work Log).
   - **Задача отсутствует** → `cron create` из спеки (name/schedule/payload verbatim;
     hourly — params.priority=10). Новый job_id пометить в worklog; НЕ обновлять
     last_known_job_id в jobs.json ради этого (он справочный).
   - **Расписание/промпт разошлись** (sha256 не совпал, expr другой) → `cron delete` по
     job_id + `cron create` из спеки. Помета в worklog: «cron restored from spec».
   - **Спека сама устарела** (автор менял промпт через чат, спеку забыли) → СНАЧАЛА
     перегенерировать спеку от живого состояния (`build_cron_specs.py` правкой JOBS в
     скрипте), закоммитить, потом чинить крон. Правило: спека меняется ТОЛЬКО осознанно
     (автор/согласованная правка), кроны — механически из спеки.
4. КРАЙНИЙ случай: `cron list` недоступен/пуст, а часовой раунд — значит и есть живой
   агент → восстановить все 3 из спеки в том же порядке (hourly → snap15 → snap35) и
   пометить «CRONS RESTORED FROM GIT» жирно в worklog + ledger.
5. Часовая задача после пересоздания сама запустится в свой fixed_rate-такт; дрейф
   расписания (fixed_rate ≠ ровно :20) — штатно, сверки привязаны к name, не ко времени.
